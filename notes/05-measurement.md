# 测量方法论

来自旧项目 `~/Projects/dlm/notes/05-measurement.md` (2026-09-26)。
那一轮抓到 4 个 bug, **其中 3 个是测量 bug**。

> 一个错误的数字比一次崩溃更贵 —— 崩溃会告诉你去看, 错误的数字不会。
> 它还不会自己暴露: 93 分钟的训练和 60 分钟的训练, 日志长得一模一样。

**这份文件是整个项目里最容易忘、代价最高的东西。**

---

## Bug 1 — 分母里混进了评估时间

**症状**: 训练循环报 `4,400 tok/s`, 隔离 benchmark 报 `5,736 tok/s`。

**原因**: 分母用了墙钟, 而 `elapsed` 里包含每 200 步一次的验证
(20 个批 + 生成一个 48 token 的样本, 约 11 s)。

```python
tok_s = (tokens_done - tokens_seen) / elapsed              # ✗
```

**修**:

```python
t_step0 = time.perf_counter()
...                        # 整个一次参数更新
train_seconds += time.perf_counter() - t_step0
tok_s = (tokens_done - tokens_seen) / train_seconds       # ✓
```

**并且两个都报**:

```
3,700 tok/s train-only     3,575 tok/s wall
```

前者用来规划 (下次要跑多久), 后者是实际会花掉的时间。

---

## Bug 2 — 累计量除以本次耗时

**症状**: 一次续训跑完, 总结行写 `11,002 tok/s`。真实值约 `5,500`。

**原因**: 分子是全局累计的, 分母是本次局部的。

**规则: 分子分母的范围必须一致 —— 都增量, 或都累计。**

---

## Bug 2 的实例: 我自己违反了一次

`scripts/bench_throughput.py` 第一版的 `wall_tps`:

```python
wall = time.perf_counter() - wall0        # wall0 在循环之前 → 含预热
wall_tps = tokens_per_step * a.steps / wall # 分子只数计时步
```

**后果**: tier1 报出 `wall_tps 5,512` vs `train_tps 8,240`, 看起来像每步有
33% 的额外开销, 于是得出了「step 外固定开销很大」的错误结论, 并据此推算出
332M token 要 16.8 小时 (实际 11.6)。

**签名 —— 看到这个比值就知道中招了**:

```
wall_tps / train_tps = (warmup + steps) / steps = 150/100 = 1.5
```

实测 8240/5512 = **1.495**。若真的是每步开销, 这个比值不会这么干净地等于
步数比。

**真正的 step 外开销只有 0.09%** (修好后测的)。两个口径在本项目里给出同一个数。

**教训**: 「我读过这份笔记」不等于「我下次不会犯」。写benchmark 脚本时
把 `warmup + steps` 一起当常量处理, 别分开算。

## Bug 3 — benchmark 太短

**症状**: 第一次测出 `5,736 tok/s / 1,897 ms/step`, 预测 20M token 跑 60 分钟。
**实际完整跑完是 93.2 分钟**, 比预测慢 1.55 倍。

**原因**: 只跑了 28 步, 全部落在前 ~300 步的快相里。

**规则: benchmark ≥ 400 步, 且先丢弃预热。**

---

## Bug 4 — 长跑接了 `tail`

15 分钟零输出, 看起来像卡死。缓冲区没刷新。

```python
# 修
sys.stdout.reconfigure(line_buffering=True)
```

`Logger()` 里的 `print(..., flush=True)` 是另一条防线, 但日志分散在多处时,
**重配一次 stdout 比给每一处加 `flush=True` 更可靠**。

**规则: 长跑不接 `tail`, 用 `tee`。**

## 日志里的 tok/s 是累计平均

这是 Bug 3 能被发现的唯一原因。日志那一列是「到目前为止的平均」,
所以一条**前 300 步快、之后恒定**的曲线, 和一条**真正逐渐变慢**的曲线,
在这一列里长得几乎一样 —— 都是单调下降然后收敛。

按区间还原真实速度:

```python
# 日志行: step N, 累计 tok/s = c   →   train_seconds(N) = N × T / c
pts = [(n, n * T / c) for n, c in rows]
for (n1, s1), (n2, s2) in zip(pts, pts[1:]):
    dt, dn = s2 - s1, n2 - n1
    print(f"{n1}->{n2}  {dn * T / dt:9,.0f} tok/s  {dt / dn * 1000:8.2f} ms/step")
```

**看到单调下降的 tok/s 曲线, 先怀疑它是累计平均。**
不要先怀疑模型, 不要先怀疑热降频。

## 有效算力 —— 决定「要不要优化」的那个数

```
FLOPs/step ≈ 6 × N_params × tokens_per_step        (前向 1× + 反向 2×)
```

```
实测 1.66 TFLOPS   ÷   实测峰值 6.8-7.3 TFLOPS   =   23%
```

**这个比例才是判断依据。**

| 观察 | 说明什么 |
|---|---|
| 显存占用 4.6 / 24 GB = 19% | **不在显存容量上** |
| 有效算力 23% | **在 kernel 效率上** |

然后**逐项测每个 kernel** 才能知道是哪个慢 —— 结论写在
`logs/dev/02-hardware-perf.md` (数字继承自 dlm 项目), 测它的脚本是
`~/Projects/dlm/test/05-sdpa-attention.py` (**本项目没搬**, 见下)。
本机的答案是 attention 的 backward。

**「整体慢」不是可行动的结论。「某个 kernel 慢 25 倍」才是。**

## 反例: 别用「吞吐对 batch 不敏感」推断「带宽受限」

2026-09-30 实测 batch 从 1 加到 64, 吞吐只涨 30% (或 53%)。
**当时据此判断「瓶颈是带宽」。这个推论是错的。**

正确的解释: attention backward 极慢, 而它的占比随 token 数上升
(T² 项), 抵消了大 batch 带来的 GEMM 效率提升 → 看起来「平坦」。

旧项目那份笔记当时的判断 (「瓶颈是 kernel 效率」) 才是对的。

**教训: 表象 → 原因这一步, 必须有一个能证伪的实验。**
当时缺的那个实验是: 单独测 attention 的 fwd 和 bwd。

## 验算: 为什么「加显存」不会更快

```
每步最少要读的权重 = 63.9 M × 2 B = 128 MB
前向读 1 次 + 反向读 2 次  = 384 MB
384 MB / 1.9 s = 202 MB/s   ← 远低于任何内存带宽
```

**(注意: 这个论证只数了权重, 没数 activation, 所以不完整。
但「不是容量问题」的结论是对的。)**

推论 —— 全部与「多用显存」相反:

| 做法 | 为什么没用 |
|---|---|
| 把 GTT 填满 | 换不来 kernel 效率; 而且 GTT 和桌面共享, 填满 = 桌面 OOM |
| 加 `--num_workers` | 数据组批只占 `0.20 ms / 1897 ms = 0.01%` |
| 梯度累积 | 显存占用**完全不变**, 只是把 batch 拆开算 |
| 更大 batch | 本机有效 (B=1→8 涨 53%), 但 B>8 无收益 |
| `torch.compile` | 可能有效 (fusion, 直接对着那 23% 去) |

## 跨实现对拍的容差 —— bf16 下不可能到 1e-5

实测 (CPU, fp32/bf16 各跑一遍同一模型, hidden 64 · 2 层 · vocab 128 · seq 32 ·
batch 2, logits 量级 max|logit| = 0.860):

| 对照 | max\|Δ\| | 相对 |
|---|---:|---:|
| fp32 跑两次 (确定性自检) | 0.00e+00 | — |
| fp32 整批[0] vs fp32 单条 | 0.00e+00 | — |
| **fp32 vs bf16 (纯舍入, 同一实现)** | **4.99e-03** | 5.8e-3 |
| fp32 vs fp16 (纯舍入) | 6.08e-04 | 7.1e-4 |
| bf16 整批[0] vs bf16 单条 | 0.00e+00 | — |

### 怎么用这个数字

| 精度 | 可达到的容差 | 适用于 |
|---|---|---|
| bf16 | `1e-2` 量级 | 便宜的对拍, 抓结构性 bug (RoPE 位置错、GQA 头数错) |
| fp32 | `1e-5` | 严对拍, 同一实现的不同写法 |
| fp32 + 独立实现 | `1e-5` 是**乐观下界** | `example/PLAN.md` C1 |

**两个独立实现 (transformers vs 手写 torch) 的差异必然大于「纯舍入」** ——
RoPE 的 cos/sin 累加顺序、`repeat_interleave` 的位置、norm 的 eps 位置、
attention 的 backend 选择, 每一项都能引入差异。

所以: **bf16 下写 1e-5 的阈值是错的, 不是实现有 bug。** 想要 1e-5 就必须
在 fp32 下对拍。fp16 比 bf16 精一个数量级 (6e-4 vs 5e-3), 但 fp16 有溢出风险,
只适合做对拍不适合做训练。

⚠️ 第一版这个测量是错的 —— dtype 参数传了但没 `.to(dtype)`, 同一对计算一次报
0.00e+00 一次报 9.12e-01。**两个数字互相矛盾时, 不要挑一个信, 重写。**
上表带确定性自检 (同一 fp32 跑两次必须报 0)。

## 从seq 扫描反推 attention 占比（假设，非测量）

**目的**：`AGENTS.md` 写「逐项测 kernel，不要只报整体数字」。用 profiler 逐kernel
测当然最好，但**扫seq_len 也能把 O(T²) 的那一项单独摘出来** —— 前提是诚实地
说清它有多少自由度。

模型 `t(T) = a + b·T + c·T²`，`c·T²` 就是 attention（fwd + bwd 合计）。
tier1（26,879,488 参数 · batch 8 · bf16 · sdpa）实测：

| seq | ms/step |
|---:|---:|
| 256 | 227.6 |
| 512 | 512.3 |
| 1024 | 1,217.0 |

三个点解三个未知数：

```
t(T) = -12.0 + 0.8479·T + 3.4409e-04·T²      (ms/step)
```

| seq | 常数项 | 线性项 (FFN+投影) | attn 项 | **attn 占比** |
|---:|---:|---:|---:|---:|
| 256 | -12.0 | 217.0 | 22.6 | 9.9% |
| 512 | -12.0 | 434.1 | 90.2 | **17.6%** |
| 1024 | -12.0 | 868.2 | 360.8 | 29.6% |

### 这跟「瓶颈是 attention backward」矛盾

在本机的 tier1 / seq 512 上，**attention 只占17.6%，逐位置的 FFN+投影占 84.7%**。
「瓶颈在 attention」是上一个项目在更大模型 / 更长上下文下的结论，直接搬过来
会误导优化方向 —— 按它去调 attention只会动到六分之一的耗时。

### ⚠️ 但这只是假设，不是测量

**残差恒等于 0，因为 3 个点解3 个未知数，自由度为 0。** 任何三个正数都能被
一个二次多项式精确穿过，这个拟合**没有任何验证能力**。常数项拟合出 -12.0 ms
（负数）已经说明它把噪声当成了信号。

**可证伪的预测**（跑一次就能验证或推翻）：

| 预测 | 若成立 → 二次模型对；若不成立 → 换模型 |
|---|---|
| T=384 → 364 ms, attn 占 13.9% | |
| T=768 → 842 ms, attn 占 24.1% | |

**要变成真测量**，至少加两个点（T=384、T=768），让残差有自由度；或者直接用
`torch.profiler` 按 kernel 名拆。**在验证之前，不要把这个占比写进任何决策。**
